[[bucket4j-ignite, Bucket4j-Ignite]]
==== Apache Ignite integration
Before using the ``bucket4j-ignite`` module, please read the <<bucket4j-jcache, bucket4j-jcache documentation>>,
because ``bucket4j-ignite`` is just a follow-up to ``bucket4j-jcache``.

Bucket4j supports the Ignite thin client as well as regular (thick client) deployment scenarios.

**Question:** Bucket4j has supported JCache since version ``1.2``. Why was direct support for ``Apache Ignite`` needed?
**Answer:** Because the https://www.jcp.org/en/jsr/detail?id=107[JCache API (JSR 107)] does not specify an asynchronous API,
developing the dedicated ``bucket4j-ignite`` module was the only way to provide asynchronous support to users who use ``Bucket4j`` together with ``Apache Ignite``.

**Question:** Should I migrate from ``bucket4j-jcache`` to ``bucket4j-ignite`` if I do not need an asynchronous API?
**Answer:** No, you do not need to migrate to ``bucket4j-ignite`` in that case.

===== Dependencies
To use the ``bucket4j-ignite`` extension, add the following dependency:
[source, xml, subs=attributes+]
----
<!-- For Java 17 -->
<dependency>
    <groupId>com.bucket4j</groupId>
    <artifactId>bucket4j_jdk17-ignite</artifactId>
    <version>{revnumber}</version>
</dependency>
----

===== Example of Bucket instantiation via IgniteProxyManager
[source, java]
----
org.apache.ignite.IgniteCache<K, byte[]> cache = ...;
private static final IgniteProxyManager<K> proxyManager = Bucket4jIgnite.thickClient()
    .entryProcessorBasedBuilder(cache)
    // setup optional parameters if necessary
    .build();
...

BucketConfiguration configuration = BucketConfiguration.builder()
    .addLimit(limit -> limit.capacity(1_000).refillGreedy(1_000, ofMinutes(1)))
    .build();
Bucket bucket = proxyManager.getProxy(key, () -> configuration);
----
IMPORTANT: `IgniteProxyManager` requires every node in the cluster to have the Bucket4j jars on its classpath.

===== Example of Bucket instantiation via the thin client
[source, java]
----
org.apache.ignite.client.ClientCache<K, byte[]> cache = ...;
org.apache.ignite.client.ClientCompute clientCompute = ...;
private static final IgniteThinClientProxyManager<K> proxyManager = Bucket4jIgnite.thinClient()
    .clientComputeBasedBuilder(cache, clientCompute)
    // setup optional parameters if necessary
    .build();
...

BucketConfiguration configuration = BucketConfiguration.builder()
    .addLimit(limit -> limit.capacity(1_000).refillGreedy(1_000, ofMinutes(1)))
    .build();
Bucket bucket = proxyManager.getProxy(key, () -> configuration);
----
IMPORTANT: `IgniteThinClientProxyManager` requires every node in the cluster to have the Bucket4j jars on its classpath.

===== Example of Bucket instantiation via the thin client and IgniteThinClientCasBasedProxyManager
[source, java]
----
org.apache.ignite.client.ClientCache<K, java.nio.ByteBuffer> cache = ...;
private static final IgniteThinClientCasBasedProxyManager<K> proxyManager = Bucket4jIgnite.thinClient()
    .casBasedBuilder(cache)
    // setup optional parameters if necessary
    .build();
...

BucketConfiguration configuration = BucketConfiguration.builder()
    .addLimit(limit -> limit.capacity(1_000).refillGreedy(1_000, ofMinutes(1)))
    .build();
Bucket bucket = proxyManager.getProxy(key, () -> configuration);
----
IMPORTANT: unlike the other two options, `IgniteThinClientCasBasedProxyManager` does not require the Bucket4j jars to be present on every cluster node, but it operates with higher latency. Choose it over `IgniteThinClientProxyManager` only if you have no control over the cluster's classpath.

===== Notes about the expiration policy
Unlike Infinispan, Coherence, and Hazelcast, Ignite does not provide an API for configuring per-entry expiration.
So there is currently only one option - configure expiration at the cache level, https://apacheignite.readme.io/docs/expiry-policies[for example, as described here].
If this is not acceptable, switch to one of the other in-memory grids mentioned above.

[[bucket4j-ignite-3, Bucket4j-Ignite-3]]
==== Apache Ignite 3.x integration
Apache Ignite 3.x is a distinct product line from Ignite 2.x, with an incompatible client API (SQL-first tables instead of caches, no ``EntryProcessor``,
and a different thin-client/transaction model). Because of that, it is packaged as a separate module rather than folded into ``bucket4j-ignite``,
and both modules are kept and maintained side by side so users on either branch keep getting Bucket4j's new features.

===== Dependencies
To use the ``bucket4j-ignite-3`` extension, add the following dependency:
[source, xml, subs=attributes+]
----
<dependency>
    <groupId>com.bucket4j</groupId>
    <artifactId>bucket4j_jdk17-ignite-3</artifactId>
    <version>{revnumber}</version>
</dependency>
----

===== Example of Bucket instantiation via IgniteKeyValueCasBasedProxyManager
This option performs a plain get/compare-and-swap dialog with a table's ``KeyValueView``, without executing any code on the Ignite server side.
Choose it when you already own a table and want the simplest possible integration.
[source, java]
----
org.apache.ignite.table.KeyValueView<K, byte[]> keyValueView = ...;
private static final IgniteKeyValueCasBasedProxyManager<K> proxyManager = Bucket4jIgnite3.INSTANCE
    .casBasedBuilder(keyValueView)
    // setup optional parameters if necessary
    .build();
...

BucketConfiguration configuration = BucketConfiguration.builder()
    .addLimit(limit -> limit.capacity(1_000).refillGreedy(1_000, ofMinutes(1)))
    .build();
Bucket bucket = proxyManager.getProxy(key, () -> configuration);
----

===== Example of Bucket instantiation via IgniteComputeProxyManager
This option executes a colocated ``ComputeJob`` on the cluster node that owns the bucket's partition, so the read-modify-write cycle happens without extra network hops.
[source, java]
----
org.apache.ignite.client.IgniteClient client = ...;
BucketTableSettings tableSettings = BucketTableSettings.customSettings("bucket_table", "id", "state");
private static final IgniteComputeProxyManager proxyManager = Bucket4jIgnite3.INSTANCE
    .computeBasedBuilder(client, tableSettings)
    // setup optional parameters if necessary
    .build();
...

BucketConfiguration configuration = BucketConfiguration.builder()
    .addLimit(limit -> limit.capacity(1_000).refillGreedy(1_000, ofMinutes(1)))
    .build();
Bucket bucket = proxyManager.getProxy(key, () -> configuration);
----
IMPORTANT: `IgniteComputeProxyManager` runs its compute job on the node that owns the bucket's partition, so that node's classloader must be able to load the job class.
Place ``bucket4j-ignite-3`` and ``bucket4j-core`` on every cluster node's classpath, or deploy them as an https://ignite.apache.org/docs/latest/developers-guide/compute/deployment-units[Ignite Deployment Unit].

NOTE: The compute job's table must have a JDK matching the one Bucket4j was built with (JDK 17) available on the server node - the officially published Ignite 3.x Docker image bundles a JDK 11 JRE by default, which cannot load the job's class files.

===== Concurrent access to the same bucket key
Both proxy managers reconcile concurrent writers to the same bucket key with an optimistic compare-and-swap loop on the row's state column,
retrying with a randomized backoff on a CAS conflict rather than relying on Ignite's own transactional isolation to detect the conflict.
